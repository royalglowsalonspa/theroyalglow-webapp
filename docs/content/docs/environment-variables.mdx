# Environment Variables

Royal Glow runs a monorepo with two Next.js apps (`apps/web`, `apps/cms`), deployed across two platforms (Cloudflare Pages + Render), and relies on ~15 external services.

<Callout type="warn">
  Environment variables are **validated at build time** using `@t3-oss/env-nextjs` + Zod. If any required variable is missing or malformed, the build fails immediately. Never use `process.env` directly — always import from `apps/web/src/env.ts`.
</Callout>

## Quick Start

```bash
# 1. Copy templates
cp apps/web/.env.example apps/web/.env.local
cp apps/cms/.env.example apps/cms/.env.local

# 2. Fill in values from your service dashboards

# 3. Generate VAPID keys (one-time only)
bunx web-push generate-vapid-keys

# 4. Validate — build fails fast if anything is missing
cd apps/web && bun run build
```

## File Structure

```
rgss_solutions/
├── .env.example               # Root template (committed)
├── .env.local                 # Local dev secrets — NEVER commit
├── apps/web/.env.example      # web-specific vars (committed)
├── apps/web/.env.local        # Local overrides (gitignored)
└── apps/cms/.env.example      # cms-specific vars (committed)
```

## Complete Variable Reference

### Database (Neon)

| Variable | Apps | Description |
| --- | --- | --- |
| `DATABASE_URL` | web, cms | Pooled connection via Neon pgBouncer — used by all app queries |
| `DATABASE_URL_UNPOOLED` | web | Direct connection — for migrations only |

> **Per-environment branches:** Use GitHub Environments so `DATABASE_URL` points to the correct Neon branch per environment (`main` / `preprod` / `test` / `dev`).

### App Configuration

| Variable | Visibility | Dev value | Prod value |
| --- | --- | --- | --- |
| `APP_ENV` | Private | `dev` | `prod` |
| `NEXT_PUBLIC_APP_URL` | **Public** | `http://localhost:3000` | `https://theroyalglow.in` |
| `NEXT_PUBLIC_CMS_URL` | **Public** | `http://localhost:3001` | `https://admin.theroyalglow.in` |

> **`NODE_ENV` vs `APP_ENV`:** `NODE_ENV` is always `development` or `production` (Next.js convention). `APP_ENV` distinguishes between our 4 deployment environments: `dev`, `test`, `pprd`, `prod`. Use `APP_ENV` for environment-specific logic.

## Platform Injection

| Platform | Where to set | Applied to |
| --- | --- | --- |
| **Cloudflare Pages** | Pages → Settings → Environment Variables | `apps/web` (edge) |
| **Render** | Service → Environment tab | `apps/web` (SSR origin) + `apps/cms` |

Both platforms inject vars at runtime — no `.env` file is needed or present in production.

## GitHub Secrets

```
Repository Settings → Secrets and variables → Actions
├── DATABASE_URL_DEV / TEST / PPRD / PROD
├── DATABASE_URL_UNPOOLED_DEV / TEST / PPRD / PROD
├── BETTER_AUTH_SECRET
├── GOOGLE_OAUTH_CLIENT_ID / SECRET
```

```yaml
env:
  DATABASE_URL: ${{ secrets.DATABASE_URL_PROD }}
  BETTER_AUTH_SECRET: ${{ secrets.BETTER_AUTH_SECRET }}
```
